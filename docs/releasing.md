# Releasing

How a `v*` tag turns into installable packages for Windows, macOS and Linux.

## What a release produces

One GitHub Release carrying:

| Artifact | Built by | For |
| --- | --- | --- |
| `sicompass-<triple>.tar.xz` / `.zip` | cargo-dist | portable archives, all four targets |
| `sicompass-installer.sh` | cargo-dist | `curl ... \| sh`, macOS and Linux |
| `sicompass-installer.ps1` | cargo-dist | `irm ... \| iex`, Windows |
| `sicompass-x86_64-pc-windows-msvc.msi` | cargo-dist | Windows installer, Start Menu entry |
| `sicompass_<version>_amd64.deb` | cargo-packager | Debian, Ubuntu, Mint |
| `sicompass-<version>-1.x86_64.rpm` | cargo-generate-rpm | Fedora, RHEL, openSUSE |
| `sicompass_<version>_x86_64.AppImage` | cargo-packager | any Linux distribution |
| `sicompass-<triple>.dmg` | cargo-packager | macOS, both architectures |
| `sha256.sum`, `SHA256SUMS-*.txt` | both | verification |
| `source.tar.gz` | cargo-dist | source |

Nix is the fifth Linux format and is not a release artifact: `packages.default`
in `flake.nix` builds from the tag directly, so `nix run
github:friendlyflow/sicompass` works with nothing published.

### Why the PowerShell installer needs help

`sicompass-installer.ps1` is generated by cargo-dist at build time from a
template aimed at command-line tools. It is not checked in, so none of the
below can be patched here.

**It aborts under the default execution policy.** It requires
`Get-ExecutionPolicy` to return `Unrestricted`, `RemoteSigned` or `Bypass`, and
Windows' default is `Restricted`.

**It closes the terminal instead of reporting the error.** Every failure goes
through a top-level `catch { ...; exit 1 }`, and `iex` runs the script in the
caller's scope, so that `exit` ends the user's PowerShell session and the
window disappears with the message still in it.

Both are why the README wraps the one-liner in
`powershell -NoProfile -ExecutionPolicy Bypass -Command "..."`. The wrapper
supplies an accepted policy and gives the installer its own process to exit.
If a cargo-dist upgrade fixes either half, simplify the README back.

**It creates no Start Menu entry.** So does the `.zip`, and so does
`cargo install`. Rather than maintain a second installer, the app registers
itself: `src/sicompass/src/start_menu.rs` writes a per-user shortcut on
startup, skipping installs under Program Files because the MSI already ships a
per-machine one. Its `SHORTCUT_NAME` and the `Name` on the `Shortcut` element
in `wix/main.wxs` must stay identical, and a unit test fails if they drift.

## The pipeline

Nothing runs as a side effect of a commit. The chain is:

```
git push origin vX.Y.Z
   -> release-on-tag.yml         (the only tag-triggered workflow)
      -> gh workflow run release.yml -f tag=vX.Y.Z
         -> release.yml "Release"      (generated by cargo-dist)
            |- plan
            |- build-local-artifacts        archives, .msi, installers
            |- custom-native-packages       -> native-packages.yml
            |     |- linux    .deb, .rpm, AppImage
            |     `- macos    .app, .dmg   (x2, one per arch)
            |- build-global-artifacts
            `- host                    FAILS with 403, see below
               -> release-publish.yml  creates the actual GitHub Release
```

`native-packages.yml` is a **reusable workflow called from inside the Release
run**, not a top-level one. That is deliberate: `release-publish.yml` triggers
on `workflow_run` of the workflow named "Release" and downloads the
`artifacts-*` from *that run*. Artifacts produced in any other run could not be
attached to the same release.

## What actually publishes the release

cargo-dist's own `host` job does, via `gh release create`. It works despite the
repo's `default_workflow_permissions` being `read`, because that is only the
*default*: the generated `release.yml` declares `permissions: contents: write`
at the top and is granted it.

`release-publish.yml` exists as a fallback for a 403 that does not currently
happen, and it has never run. Its `workflow_run` trigger does not fire, because
`release-on-tag.yml` dispatches `release.yml` on the **tag** ref, and
`workflow_run` does not deliver for runs on non-branch refs. If the `host` job
ever does start failing, that file would first need a `workflow_dispatch`
trigger taking a run id.

Earlier revisions of this document claimed the `Release` run always goes red
and that `release-publish.yml` does the real work. The v0.1.9 release disproved
both. Judge a release by the Releases page and the asset count either way.

## Pre-release checklist

Since nothing runs on commit, all of this is manual.

1. Bump `version` in `[workspace.package]` in the root `Cargo.toml`. The flake
   reads it from there, so nothing else needs bumping.
2. Update `CHANGELOG.md`. cargo-dist parses it into
   `announcement_github_body`, which `release-publish.yml` writes into the
   release notes verbatim. Without an entry the notes are generic boilerplate.
3. Run **CI** by hand (Actions -> CI -> Run workflow). It covers Linux, macOS
   and Windows, and includes a `dist generate --check`.
4. Run **Licenses** by hand if dependencies changed. `about.toml` covers all
   four target triples, so a dependency added on any one platform can move
   `THIRD-PARTY-LICENSES.html`.
5. Confirm `[patch.crates-io]` in the root `Cargo.toml` is still commented out.
   It is exactly the kind of thing that gets uncommented while debugging.
6. `git tag vX.Y.Z && git push origin vX.Y.Z`.

## Regenerating things

`release.yml` is **generated**. Never hand-edit it. Change
`dist-workspace.toml`, then:

```sh
cargo install cargo-dist --version "$(grep -oP 'cargo-dist-version = "\K[^"]+' dist-workspace.toml)" --locked
dist generate
```

`dist` is deliberately not in the flake: it must match `cargo-dist-version`
exactly, and nixpkgs tracks its own cadence, so a flake-pinned copy would drift.

`src/sicompass/wix/main.wxs` **is** hand-edited (it installs `assets/`, adds a
Start Menu shortcut and sets the product icon), which is why
`allow-dirty = ["msi"]` is set. dist will never refresh that file, so when
upgrading cargo-dist, diff its new template against ours by hand.

Shaders and icons are also committed rather than built:

```sh
nix develop -c ./scripts/gen-shaders.sh   # after editing shaders/*.vert|frag
nix develop -c ./scripts/gen-icons.sh     # after editing assets/icons/*.svg
```

Each script's header explains why. `cargo test -p sicompass` fails if the
shaders drift.

## Post-release smoke test

The pipeline can publish artifacts that do not run, and has done exactly that
before, so check the real thing:

- **Any platform**: `sicompass --check`. It reports the resolved resource root
  and the Vulkan devices it can see, which is the whole class of failure that
  used to only appear on a user's machine.
- **Linux**: install the `.deb` on a clean Ubuntu container and run it. Then
  run the AppImage on a *different* distribution: linuxdeploy bundling a
  `libvulkan.so.1` that shadows the host's ICDs is the classic failure, which
  is what `excluded-libs` guards against.
- **Linux, icons**: on a real desktop, confirm the app menu entry has an icon
  *and* that the running window has one in the taskbar and in alt-tab. These
  are two different mechanisms and each has failed on its own. The menu entry
  needs the icon cache refreshed on install, which is
  `src/sicompass/deb/postinst` for the `.deb` and `post_install_script` in
  `src/sicompass/Cargo.toml` for the `.rpm`. The window icon comes from
  `icon.rs`, which embeds the PNG and pins the `app_id`, and is the only thing
  covering installs that ship no `.desktop` file at all: the archives, the
  `curl | sh` installer, `nix run`, and an un-integrated AppImage.
- **macOS**: mount the `.dmg`, drag to Applications, clear the quarantine flag,
  and confirm it renders and that VoiceOver reads the tree.
- **Windows**: run the `.msi`, confirm the Start Menu entry and the icon, and
  confirm the tutorial finds its images (that is `assets/` being installed by
  the components in `main.wxs`). Check the Start Menu entry by pressing the
  Windows key and typing `sicompass`, not by scrolling the app list. Search
  matches word prefixes in the shortcut name, so a name that reads fine in the
  list can still be unreachable by the one word every user knows.
- **Windows, second pass**: run the PowerShell installer on a machine with no
  MSI install, launch sicompass once, and confirm a Start Menu entry appears
  and that there is exactly one. That is `start_menu.rs` covering the
  installer that cannot ship a shortcut of its own.

## What the packages assume

Shaders and fonts are compiled into the binary, so the only runtime tree is
`assets/`. `resources::resource_root()` finds it by probing, in order:
`$SICOMPASS_RESOURCE_DIR`, the executable directory, its parent,
`../Resources` (macOS `.app`), `../lib/sicompass` (deb, rpm, AppImage),
`../share/sicompass` (Nix), the repository root, then the working directory.

**`include` in `dist-workspace.toml` populates the archives only.** The shell
installer, the PowerShell installer and the MSI copy binaries and nothing else.
Anything the app needs at runtime must either be embedded in the binary, or
added explicitly to `wix/main.wxs` and to the cargo-packager `resources` list.
Forgetting this is what made every release up to 0.1.8 unable to start.
